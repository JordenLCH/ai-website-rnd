Practitioner reference · How websites were designed and built before generative AI

The Pre-AI Web Studio

The human pipeline — discovery, IA, wireframe, comp, prototype, build, QA — and the do/don't rules each role earned the hard way. Everything below predates AI generation, and most of it is the reason AI-generated sites either work or don't.

Roles: UX · UI · Frontend Era covered: 1995–2026 Compiled 2026-09-07
Part one

The pipeline a studio actually runs

Seven phases, in order, because each one's output is the next one's input — that dependency is the whole reason the sequence exists. Durations are typical agency figures for a 12–24 week marketing site; a product team compresses these into sprints but does not skip them.

01

Discovery & research

Stakeholder interviews, competitor teardown, analytics of the old site, user interviews. Ends with agreement on who this is for and what one action matters — not on any visual.

Artifact: creative brief · personas · JTBD statements · success metrics
2–3 weeks
02

Information architecture

Card sorting and tree testing produce a sitemap and URL structure. Content inventory happens here: every page gets an owner and a word count before anyone draws a box.

Artifact: sitemap · user flows · content matrix · URL scheme
1–2 weeks
03

Wireframes

Greyscale, no type personality, no photography. Deliberately ugly so the review is about hierarchy and sequence, not colour. Cheap to throw away — that is the point.

Artifact: low-fi wireframes at 2–3 breakpoints · annotated states
2–3 weeks
04

Visual design / comps

Art direction lands: type scale, palette, grid, photography treatment, motion language. Historically one flat comp per key page; since ~2013 a component library plus two or three key screens.

Artifact: mood board / style tiles · hi-fi mockups · design tokens · component library
2–4 weeks
05

Prototype & validate

Clickable flow tested on 5 users per round — the number at which most usability problems in a flow surface. Fix in the prototype, where a change costs an hour instead of a sprint.

Artifact: interactive prototype · usability findings · revised screens
1–2 weeks
06

Build

Components first, pages second. Content is loaded from the CMS early, because real copy breaks layouts that lorem never does. Handoff is a conversation, not a file drop.

Artifact: component library in code · CMS models · staging environment
4–8 weeks
07

QA, launch, iterate

Cross-browser and device matrix, keyboard and screen-reader pass, performance budget check, redirect map for every old URL. Post-launch is where the analytics loop starts, and it never closes.

Artifact: QA matrix · a11y audit · redirect map · analytics dashboard
1–2 weeks + ongoing
Part two

How the tools changed the flow

Each shift below moved where design decisions get made — from the print-style comp, to the browser, to a shared component library. The direction of travel is one-way: away from drawing pages, toward defining systems.

1995–99
Print workflow, web output

Layouts nested in <table> with spacer.gif. Designers handed pixel-exact comps because pages were fixed-width and the browser was treated as paper.

Photoshop 5.5 + ImageReady · "Save for Web" (1999) · slicing
2000–06
CSS separation of concerns

Standards movement pushes structure into HTML and presentation into CSS. "PSD to HTML" becomes a job title — one person draws, another rebuilds it in markup.

CSS 2.1 · float layouts · Dreamweaver · Firebug (2006)
2007–09
The grid era

960px, 12 columns, everywhere. Shared grid made handoff mechanical, and made every site of the period look related.

960.gs · Blueprint · jQuery
2010–12
Responsive breaks the comp

Ethan Marcotte names responsive web design in 2010: fluid grid, flexible images, media queries. A static comp can no longer describe a page that has no fixed width, so studios adopt style tiles, element collages and designing in the browser.

Media queries · mobile-first · Bootstrap (2011)
2013–17
Symbols and the design system

Sketch makes vector, artboard-based UI work fast, and its symbols make reuse the default unit of design. Atomic design and pattern libraries give designers and developers one shared vocabulary.

Sketch · InVision · Zeplin · Atomic Design (2013)
2018–26
Multiplayer, token-driven

Figma moves the file to the browser and kills version-conflict handoff. Components + variants + variables map nearly one-to-one onto coded components and CSS custom properties, so the design file and the codebase describe the same system.

Figma · design tokens · Storybook · CI visual regression
The lasting lesson of responsive design: a page is not a picture. The moment a deliverable stops being a fixed image, the deliverable becomes the system that generates images. Why studios ship component libraries, not page mockups
Part three · UX designer

Do & don't: structure, flow, research

Rooted in Nielsen's 10 usability heuristics (1994) — still the field's working checklist because they describe human memory and attention, not any interface fashion.

Do

Decide the page's single job before drawing anything, and let one primary action own the hierarchy.

Two equal CTAs means the page has no CTA.

Don't

Start in a visual tool. Colour and type conversations crowd out structure conversations and always win.

Stakeholders review what they can see.

Do

Show system status: loading, saving, saved, error. Every action gets feedback within 1 second, or it gets a spinner.

Heuristic 1 — visibility of system status.

Don't

Invent labels from the system's vocabulary. Users manage notifications, never webhook configs.

Heuristic 2 — match to the real world.

Do

Give every destructive path an exit: undo, confirm, or back. Assume the user got here by accident.

Heuristic 3 — user control and freedom.

Don't

Rely on recall. If a value is needed in step 4, show it in step 4 — don't ask users to remember step 2.

Heuristic 6 — recognition over recall.

Do

Test with 5 users per round, then fix and re-test. Rounds beat sample size.

Diminishing returns set in fast within one flow.

Don't

Treat stakeholder opinion as user data. Record the disagreement, then resolve it with a test.

The loudest room voice is not the segment.

Do

Design the empty, loading, error, partial and overflowing states alongside the happy path.

Real content is uneven; only mockups are tidy.

Don't

Ship a flow you have not walked keyboard-only, top to bottom, with no mouse.

Keyboard traps are found in 30 seconds or never.

Do

Write error messages that name the cause and the fix. "Card declined — try another card or contact your bank."

Heuristic 9 — help users recover.

Don't

Use mystery-meat navigation: icon-only controls with no label and no accessible name.

An icon is a mnemonic, not a definition.

Part four · UI / visual designer

Do & don't: type, colour, grid, system

The craft layer. Most of what separates a designed page from a generated one lives in spacing discipline and type scale, not in the palette.

Do

Set a type scale (e.g. 1.25 ratio) and a spacing scale (4 or 8px base), then stay on both.

Arbitrary values are what "unpolished" actually means.

Don't

Use more than 2–3 typefaces, or more than ~4 weights. Contrast comes from size and weight, not variety.

Every extra face is another 30–120 KB too.

Do

Keep running text at 45–75 characters per line and body size ≥16px on mobile.

Below 16px, iOS Safari zooms your form on focus.

Don't

Encode meaning in colour alone — pair every status colour with an icon, label or shape.

~8% of men cannot separate your red from your green.

Do

Design mobile-first, then let the layout earn extra columns. Constraint sorts the hierarchy for you.

Widening a good small layout is easy; the reverse is not.

Don't

Design against lorem ipsum or perfectly cropped stock. Use the client's real longest product name.

Real copy is the stress test the comp skipped.

Do

Define tokens (colour, space, radius, shadow, motion) and name them by role — surface-raised, not grey-200.

Role names survive a rebrand; hex names don't.

Don't

Put a border, a radius and a shadow on everything. If every block is a card, nothing is emphasised.

Separation devices are budget — spend them by role.

Do

Give interactive elements all five states: rest, hover, focus-visible, active, disabled.

Focus is the one everyone forgets and auditors check first.

Don't

Animate for its own sake. Motion should explain a relationship (where a panel came from), 150–300 ms, and respect prefers-reduced-motion.

Motion is an explanation, not a garnish.

Do

Hand over redlines the system can hold: components, variants, tokens, and the rules for when to use each.

Deliver the system, not the screenshot.

Don't

Deliver a pixel-exact comp for one width and call it responsive.

The gaps get invented by whoever builds it.

Part five · Frontend developer

Do & don't: markup, performance, resilience

The build layer, where design intent either survives or quietly degrades into a slow, inaccessible approximation of itself.

Do

Reach for the semantic element first — button, nav, main, label, real headings in order.

Free keyboard, focus and screen-reader behaviour.

Don't

Rebuild a native control out of divs and ARIA. ARIA patches semantics; it never adds behaviour.

"No ARIA is better than bad ARIA."

Do

Set a performance budget in CI and fail the build on regression — e.g. ≤400 KB gzipped JS on interactive pages.

Unbudgeted bundles only grow.

Don't

Ship layout-shifting media. Every image and embed gets explicit width/height or aspect-ratio.

This is most of a bad CLS score.

Do

Build components once, use them everywhere, and let content come from data — never duplicate markup per page.

A fix to one component fixes every page that uses it.

Don't

Hand-write per-page markup for a site that must be re-themed or patched fleet-wide later.

Bespoke markup is un-migratable; it has no undo.

Do

Test the matrix that matters: latest two versions of Chrome/Safari/Firefox/Edge, plus a real low-end Android.

Your laptop is not the p75 device.

Don't

Block first paint on webfonts. Use font-display:swap, preconnect, and a metric-compatible fallback stack.

Invisible text is a blank page to the user.

Do

Validate input server-side as well as client-side, escape output, and treat every client value as hostile.

Client validation is UX; server validation is security.

Don't

Let the page depend on JavaScript for content that could be HTML. Server-render what can be read.

Crawlers, slow links and JS errors all read HTML.

Do

Measure with field data (RUM at p75), not just a lab run on your own machine.

Lab scores flatter; field scores rank.

Don't

Leave accessibility to a pre-launch "audit sprint". Bake it into the component, once.

Retro-fixing 40 pages costs 40× fixing one component.

Part seven

The handoff contract

What a designer owes a developer, and the reverse. Where handoff fails, it is almost always one of these six items being assumed rather than stated.

Tokens, not values

Colour, spacing, radius, type scale and motion durations as named variables that map to CSS custom properties.

States, all five

Rest, hover, focus-visible, active, disabled — plus empty, loading, error for any data view.

Breakpoint behaviour

What reflows, what hides, what changes order. Two widths designed, the rule stated for everything between.

Content rules

Max characters per field, truncation vs. wrap, what happens when the image is missing or portrait.

Accessible names

The label a screen reader announces for every icon-only control, and the heading order for the page.

Back from the dev

Which parts were impossible or expensive, and what shipped instead — so the design file matches production.

Part eight

What generation changes, and what it can't

  • Compressed: phases 03–04. Wireframe and comp used to cost weeks; a generator produces candidate layouts in minutes, so their value shifts from production to selection.
  • Unchanged: phases 01–02. Discovery and IA depend on facts only the client holds — legal name, real prices, actual staff, what the business is trying to sell. Nothing invents those safely.
  • More important, not less: phase 07. Generated output needs the same QA matrix, the same keyboard pass and the same performance budget — with the added job of checking nothing was fabricated.
  • The new failure mode: plausible sameness. Human studios diverged because they had different clients, constraints and taste; a model's first proposal is the mode of its training data, so the discipline is to generate several directions and deliberately discard the likeliest.
  • The durable rule: ship a system, not pages. Bespoke markup could never be patched fleet-wide in 2005 and still can't in 2026 — which is exactly why generated sites should be structured content plus a swappable theme, not hand-written HTML.
